### Fixed in v2.7.1

The fixes of the v2.7.0 VM round.

- **Dedicated CPUs for VMs need KubeVirt's `CPUManager` gate** (#111). With `kubelet.cpuManagerPolicy: static`, a VM with `dedicatedCpuPlacement: true` stays `ErrorUnschedulable` until the gate is on. On KubeVirt 1.9 the gate is Alpha and off by default, and without it virt-handler never labels the nodes `cpumanager=true`.
  - The k4all addon 0.2.1 says so on the Node settings page: while the static policy is set, Virtualization is on and the gate is off, it links to the gates of the Virtualization page.
  - To turn it on, use the Virtualization page (*KubeVirt feature gates*) or `features.virt.kubevirt.featureGates: [CPUManager]`. The nodes get their labels within a minute. KubeVirt's infra and running VMs do not restart.
  - docs/upgrades.md, *Node settings*, says it too, along with two more findings of the VM round:
    - a change of kernel arguments makes a new deployment of the same release, so afterwards `bootc rollback` boots the same release with the old arguments;
    - a 2-node `smallCluster: Allow` Ceph cluster stays HEALTH_WARN `TOO_FEW_OSDS`, and how to clear it.
- **`k4all-upgrade status` no longer calls a newer release a rollback** (#112). After `sync-manifest` finishes the sync an abandoned hop left behind, the node runs the newer release. Status now prints `Committed: <committed>; the node runs <booted>, a newer release whose hop was abandoned after its reboot (not a rollback)`. An older release still gets the `Rollback:` line. The line comes from the tool of the release the node runs, so it is right once the node runs v2.7.1.
- **k4all-operator v0.6.1** (from v0.6.0, through the manifest sync):
  - virt-operator no longer rolls out twice at each KubeVirt apply. Every ClusterConfig change re-applies KubeVirt. v0.6.0 wrote upstream's Deployment and then the release's patch, two rollouts each time. v0.6.1 writes the patched object once. The other components with release patches (metrics-server, Multus, ovs-cni) also roll only once when they are applied ([k4all-operator#44](https://github.com/gpillon/k4all-operator/issues/44)).
  - The removal of kubevirt-manager now deletes its image catalog CRD `images.kubevirt-manager.io` when the catalog holds no images. v0.6.0 left the empty CRD behind. On a cluster v2.7.0 left with it, v0.6.1 deletes it a few seconds after it starts during the hop. A catalog that holds images is kept ([k4all-operator#45](https://github.com/gpillon/k4all-operator/issues/45)).
  - Turning Rook off, or removing snapshot-controller, is no longer refused with "cannot tell whether … may be uninstalled" when a CRD the check lists is gone. A list that the API server answers with 404 counts as empty ([k4all-operator#47](https://github.com/gpillon/k4all-operator/issues/47)).
  - **A Helm release k4all did not write last no longer loses values silently** (#114). This covers a release installed or upgraded by hand, or restored from 1.x. If k4all's values for the first upgrade would drop or change any of the release's own values, the release keeps running untouched. The component is Failed with a message that names those values, and the ReleaseManifest gets the condition `ValuesDropRefused`. This holds for every Helm component. A release that k4all-operator wrote last, by any version, is never held. See *Clusters restored from 1.x: Cilium to Managed* below.
  - On a cluster without kube-proxy (one restored from 1.x), Cilium keeps its API server address when it goes from Unmanaged to Managed. The operator sets `k8sServiceHost` and `k8sServicePort` from kubeadm's `controlPlaneEndpoint`, otherwise from the address the API server advertises. If it finds neither, Cilium is not applied, and the message says to set both in `componentOverrides.cilium` (#114).
  - k4all-metadata v0.6.1, the same tag.

### Upgrading from v2.7.0

- **v2.7.1 is a patch.** Nodes in `mode: auto` take it on their own in the maintenance window. Otherwise, run `sudo k4all-upgrade plan`, then `sudo k4all-upgrade run`, or start a ClusterUpgrade from the addon's Upgrades page. Nodes on v2.6.x reach it through v2.7.0, which stays a mandatory stop.
- **The hop:** new image and reboot. Then, on the bootstrap node, the sync starts k4all-operator v0.6.1 first and applies the components after it. Headlamp restarts with the k4all addon 0.2.1. Kubernetes, CRI-O, Fedora and the other components are unchanged. In the VM tests only k4all-operator and Headlamp restarted. Clusters with kube-proxy, which is every cluster installed with 2.x, see no change to Cilium.

### Clusters restored from 1.x: Cilium to Managed

A cluster restored from 1.x runs Cilium `Unmanaged`, often with values set by hand and without kube-proxy. To hand Cilium to k4all once the cluster runs v2.7.1:

1. Run `helm get values cilium -n kube-system`. Set in the ClusterConfig what k4all has its own setting for, such as `networking.cni.cilium.l2announcements: true` for L2 announcements. Carry every other value you keep under `spec.componentOverrides.cilium.values`, for example `egressGateway.enabled`, `bpf.masquerade`, `operator.replicas` and `cluster.name`. Leave out `k8sServiceHost` and `k8sServicePort`, because k4all sets them.
2. Set `spec.components.cilium.management: Managed` on the ReleaseManifest. If k4all would still drop values, Cilium keeps running untouched and the component names them. In the VM tests, with the four values above carried but without the L2 setting, it read:

   > not taking over: revision 4 of the Helm release cilium was written by Helm, not by k4all-operator, and the values k4all applies would drop or change these of its values: k8sClientRateLimit.burst, k8sClientRateLimit.qps, l2announcements.enabled, routingMode, tunnelProtocol (to keep them, carry them in the ClusterConfig's componentOverrides.cilium values; to drop them, annotate the ReleaseManifest with k4all.magesgate.com/allow-values-drop: cilium=4)

3. Carry the listed values, or accept the drop of exactly that revision with `kubectl annotate releasemanifest k4all k4all.magesgate.com/allow-values-drop=cilium=<N>`. Values that equal the chart's defaults can be dropped: `routingMode: tunnel`, `tunnelProtocol: vxlan`, and `k8sClientRateLimit` with qps 10 and burst 20.
   - **Do not drop `l2announcements.enabled`** while Services use L2-announced LoadBalancer IPs. At the agents' next restart they stop announcing them, and those IPs stop answering. Set `networking.cni.cilium.l2announcements: true` first.
4. k4all writes Cilium's values to `cilium-config`, and the agents read them when they start. Restart them once while you are watching, so a missing value shows now and not at the next reboot: `kubectl -n kube-system rollout restart ds/cilium deploy/cilium-operator`.
