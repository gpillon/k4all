### Fixed in v2.7.1

The fixes of the v2.7.0 VM round.

- **Dedicated CPUs for VMs need KubeVirt's `CPUManager` gate** (#111). With `kubelet.cpuManagerPolicy: static`, a VM with `dedicatedCpuPlacement: true` stays `ErrorUnschedulable` until the gate is on. On KubeVirt 1.9 the gate is Alpha and off by default, and without it virt-handler never labels the nodes `cpumanager=true`.
  - The k4all addon 0.2.1 says so on the Node settings page: while the static policy is set, Virtualization is on and the gate is off, it links to the gates of the Virtualization page.
  - To turn it on, use the Virtualization page (*KubeVirt feature gates*) or `features.virt.kubevirt.featureGates: [CPUManager]`. The nodes get their labels within a minute. KubeVirt's infra and running VMs do not restart.
  - docs/upgrades.md, *Node settings*, says it too, along with two more findings of the VM round:
    - a change of kernel arguments makes a new deployment of the same release, so afterwards `bootc rollback` boots the same release with the old arguments;
    - a 2-node `smallCluster: Allow` Ceph cluster stays HEALTH_WARN `TOO_FEW_OSDS`, and how to clear it.
- **`k4all-upgrade status` no longer calls a newer release a rollback** (#112). After `sync-manifest` finishes the sync an abandoned hop left behind, the node runs the newer release. Status now prints `Committed: <committed>; the node runs <booted>, a newer release whose hop was abandoned after its reboot (not a rollback)`. An older release still gets the `Rollback:` line. The line comes from the tool of the release the node runs, so it is right once the node runs v2.7.1.
- **k4all-operator v0.6.1** (from v0.6.0, through the manifest sync):
  - virt-operator no longer rolls out twice at each KubeVirt apply. Every ClusterConfig change re-applies KubeVirt. v0.6.0 wrote upstream's Deployment and then the release's patch, two rollouts each time. v0.6.1 writes the patched object once. The other components with release patches (metrics-server, Multus, ovs-cni) also roll only once when they are applied ([k4all-operator#44](https://github.com/gpillon/k4all-operator/issues/44)).
  - The removal of kubevirt-manager now deletes its image catalog CRD `images.kubevirt-manager.io` when the catalog holds no images. v0.6.0 left the empty CRD behind ([k4all-operator#45](https://github.com/gpillon/k4all-operator/issues/45)).
  - Turning Rook off, or removing snapshot-controller, is no longer refused with "cannot tell whether … may be uninstalled" when a CRD the check lists is gone. A list that the API server answers with 404 counts as empty ([k4all-operator#47](https://github.com/gpillon/k4all-operator/issues/47)).
  - On a cluster without kube-proxy (one restored from 1.x), Cilium keeps its API server address when it goes from Unmanaged to Managed: the operator sets `k8sServiceHost` and `k8sServicePort` (#114).
  - k4all-metadata v0.6.1, the same tag.

### Upgrading from v2.7.0

- **v2.7.1 is a patch.** Nodes in `mode: auto` take it on their own in the maintenance window. Otherwise, run `sudo k4all-upgrade plan`, then `sudo k4all-upgrade run`, or start a ClusterUpgrade from the addon's Upgrades page. Nodes on v2.6.x reach it through v2.7.0, which stays a mandatory stop.
- **The hop:** new image and reboot. Then, on the bootstrap node, the sync starts k4all-operator v0.6.1 first and applies the components after it. Headlamp restarts with the k4all addon 0.2.1. Kubernetes, CRI-O, Fedora and the other components are unchanged.
