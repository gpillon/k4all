
### New in v2.7.0

- **Hangar replaces kubevirt-manager.** [Hangar](https://github.com/kalik1/hangar) v0.1.1 is the VM console in Headlamp, installed with Virtualization.
  - The component `hangar` brings Hangar's ClusterRoles and its delete protection (a ValidatingAdmissionPolicy): a VM, DataVolume or PVC labelled `hangar.magesgate.com/protected: "true"` cannot be deleted until the protection is turned off.
  - `hangar-node-agent` is a privileged DaemonSet (namespace `hangar-system`) behind Hangar's Hardware tab and PCI passthrough. It is installed by default with Virtualization; `features.virt.hangar.nodeAgent: false` leaves it out.
  - kubevirt-manager is `management: Removed` in the release. What its removal deletes and keeps: see *Upgrading from v2.6.x*.
- **Rook/Ceph, optional** (`features.rook`), with the [Cairn](https://github.com/kalik1/cairn) console v0.1.1.
  - `features.rook.enabled: true` installs Rook 1.21.2 (`rook-ceph`), the Ceph CSI RBD driver (`ceph-csi-drivers` 1.1.0) and Cairn, with Ceph v20.2.4.
  - k4all then creates, once: the CephCluster, the pool `vm-pool`, the StorageClass `ceph-rbd` (RWX Block, so VMs can live-migrate), the VolumeSnapshotClass `ceph-rbd-snapshot` and the CDI StorageProfile. OSDs go on every blank disk: a disk with a filesystem or an LVM signature is skipped, so the OS disk and TopoLVM's volume group are safe. `features.rook.storage.deviceFilter` (a regular expression such as `^sdb$`) narrows it.
  - **3 nodes by default.** Below 3 schedulable nodes nothing is created: the component reads `waiting: …` and `RookReady` is False (`NotEnoughNodes`). `features.rook.smallCluster: Allow` creates it anyway, with 1 mon and a pool size equal to the node count. That means no redundancy: a failed disk loses data. With fewer than 3 OSDs Ceph stays in HEALTH_WARN (`TOO_FEW_OSDS`); the pool works.
  - Once created, Cairn manages it (daemon counts, pools, Ceph settings). Changing `storage` or `smallCluster` afterwards does nothing. k4all keeps only the Ceph image (`spec.cephVersion.image`) of a CephCluster it created, so Ceph follows the release. A CephCluster that existed before keeps its own image. An object an admin deleted is not created again.
  - The condition `RookReady` on the ClusterConfig follows the CephCluster's phase and Ceph's health.
  - **Turning Rook off is refused while a CephCluster exists.** The Storage page lists the steps. **k4all never wipes disks.** Before turning Rook on again, wipe `/var/lib/rook` on every node and the disks the OSDs used.
  - **Memory.** Rook requests 1 GiB per OSD and 512 MiB per mon and mgr. With Virtualization too, plan at least 8 GiB per node: in the VM tests, 5 GiB workers had their memory requests full once another node was drained, and a VM could not be moved off.
- **Node settings** (`spec.nodes`, #60), the same on every node:
  - `kubelet.maxPods`: kubelet restarts, no drain.
  - `kubelet.cpuManagerPolicy`, `reservedSystemCPUs`, `topologyManagerPolicy`, `topologyManagerScope`: the node is drained, the CPU and memory manager state files are removed, kubelet restarts.
    - For VMs with dedicated CPUs (`dedicatedCpuPlacement`), also turn on KubeVirt's `CPUManager` gate on the Virtualization page. On KubeVirt 1.9 it is off by default, and without it those VMs stay unschedulable (#111).
  - `hugepages` (`1Gi`, `2Mi`), `iommu`: the node is drained and reboots with new kernel arguments. k4all only touches the kernel arguments it added itself.
  - Kubelet fields go to `kube-system/kubelet-config`, so nodes that join later get them. `k4all-upgrade agent` applies them on each node.
  - **One node at a time:** workers, then control planes, then the bootstrap node, and the node that runs k4all-operator last. `spec.nodes.rollout.paused: true` stops before the next node. A rollout never runs during a ClusterUpgrade or a hop.
  - **Clearing a field** puts back what `kubelet-config` had before k4all first wrote it. maxPods goes back to kubeadm's 250, not to the kubelet's 110.
  - The operator refuses settings that do not fit a node, and names the node: reserved CPUs that do not exist, hugepages above 80 % of the smallest node's memory (the addon warns from 50 %), maxPods above the node's pod CIDR (250 with Cilium's /24).
  - Progress is in `status.nodes` and the condition `NodeSettingsRollout`. See docs/upgrades.md, *Node settings*.
- **KubeVirt settings** (`features.virt.kubevirt`):
  - `featureGates`: k4all adds these to the gates set by others. `disabledFeatureGates`: k4all removes these, and on KubeVirt 1.8 and later also writes them to `disabledFeatureGates`.
  - The KubeVirt CR's annotations `k4all.magesgate.com/feature-gates` and `k4all.magesgate.com/disabled-feature-gates` say which gates are k4all's. Removing a gate from the ClusterConfig removes only a gate k4all added. Gates set by Hangar or by hand stay.
  - `vmStateStorageClass`: where VMs keep their persistent EFI and TPM state.
  - The API refuses a gate that is both on and off, and HotplugVolumes together with DeclarativeHotplugVolumes. The condition `KubeVirtSettings` is False for a missing StorageClass (`StorageClassNotFound`; the value is still written) or an exclusive gate pair (`ExclusiveGate`).
  - New installs own no gates.
- **Metadata service for VMs** (`features.virt.metadata`) on `169.254.169.254`:
  - OpenStack and EC2 formats (IMDSv2 too): instance-id (the VM's UID, stable across restarts), hostname, the SSH keys of `accessCredentials`, the user-data of the VM's cloud-init volume, and vendor-data from the ConfigMap named in `vendorDataConfigMap`.
  - Workload-identity tokens at `GET /k4all/v1/token?audience=<a>` for the audiences in `tokens.audiences` (default `k4all-metadata`; the Kubernetes API server rejects them). The VM's ServiceAccount comes from the label `k4all.magesgate.com/service-account`.
  - **Opt-in label:** with `scope: Labelled` (the default) a VM opts in with the template label `k4all.magesgate.com/metadata: enabled`. Hangar's wizard sets it. `scope: All` serves every VM where it is allowed.
  - **Chassis asset tag:** cloud-init looks for the service only when the VM's chassis asset tag is `OpenStack Nova`. k4all sets it on a served VM's VMI when the VM's spec has none. A VM's own tag stays, and the VM gets the Warning Event `MetadataChassisAsset`.
  - **PodSecurity:** namespaces that enforce `baseline` or `restricted` are skipped, because the injected init container needs NET_ADMIN. Their VMs start as before, keep their cloud-init disk, and get the Event `MetadataNotServed`.
  - A VM needs a pod-network (masquerade) interface.
  - The service is on for new installs with Virtualization, and off on existing clusters until you set `enabled: true`. The condition `MetadataService` shows its state.
  - The server runs inside each VM's pod (image `ghcr.io/gpillon/k4all-metadata`, the operator's version). A MutatingAdmissionPolicy injects it, with no webhook. The policy uses `failurePolicy: Ignore`, so a broken policy does not stop VMs from starting.
- **Cilium's pool on new installs** (#72). A new Cilium cluster takes its pod pool from `spec.cluster.podNetwork` (default `10.100.0.0/18`, a /24 per node, room for 64 nodes). Before, Cilium used its chart default `10.0.0.0/8`, and the third node got `10.0.2.0/24`, KubeVirt's masquerade network: its VMs could not reach pods on their own node.
  - The condition `PodNetworkOverlap` (Cilium only) checks the pool and each node's pod CIDR against the node subnets, KubeVirt's network, ingress IPs and the API VIP. It reports `OverlapFound` (True) with each overlap and what to do, `NoOverlap` (False), or `CheckFailed` (Unknown). It changes nothing.
- **snapshot-controller** (external-snapshotter v8.7.0) is a component, installed with Virtualization or Rook. Hangar's snapshots and `ceph-rbd-snapshot` need it. Its uninstall is refused while VolumeSnapshots exist, and it keeps the snapshot CRDs.
- **k4all addon 0.2.0:**
  - new pages **Virtualization** (`/k4all/settings/virtualization`), **Node settings** (`/k4all/settings/nodes`, with the plan before saving and the rollout with Pause/Resume) and **Storage** (`/k4all/settings/storage`);
  - a `PodNetworkOverlap` banner in Settings;
  - kubevirt-manager on the Components page, with what its removal kept;
  - advice for a drain held by a PodDisruptionBudget or by pods that declare no controller, on the Upgrades and Node settings pages;
  - with an operator before v0.6.0 the new pages are read-only.
- **Upgrade guards** (#77, #74, #76):
  - A ReleaseManifest that pins a component below its `installedVersion` leaves the component running as it is. The component goes `Failed` (`not downgrading: …`) and the ReleaseManifest gets the condition `DowngradeRefused`. To allow a downgrade, annotate the ReleaseManifest with `k4all.magesgate.com/allow-downgrade: "<component>=<version>[,…]"`. Each entry allows exactly that version. A pin that is not semver is never refused. This includes the operator itself: a manifest sync that would lower it ends in a HOLD on the host.
  - A ClusterConfig whose `k4all.magesgate.com/migrations` count is higher than the operator knows stops every component reconcile, uninstalls included. The condition `MigrationsAhead` is set on the ClusterConfig and the ReleaseManifest. That operator does not update itself either: run a newer operator, or check and lower the count.
  - `k4all-upgrade` and ClusterUpgrade no longer leave a stream before reaching its latest patch. When no hop reaches that patch, the plan stops with "cannot leave vX before reaching vY, the latest patch of its stream" (ClusterUpgrade: `NoPath`).
  - When a hop that syncs its ReleaseManifest is abandoned after its reboot on the bootstrap node, the node remembers that the sync is still due. `status` shows a `Sync:` line, and no new hop starts until `sudo k4all-upgrade sync-manifest` runs, or `clear-hold --sync-done` says the manifest got there another way.
- **The operator leaves the node it drains** (#97). In a ClusterUpgrade and in the node-settings rollout, the node that runs the operator goes last among its type. Once every other pod has left that node, the operator evicts its own pod, and the next leader drives the rest from another node. Before, the leader went down with the node's reboot.
- The installer's kickstart accepts every new ClusterConfig field, checked as the CRD checks them.
- k4all-operator v0.6.0 (includes v0.5.8).

### Changed

- **Turning a feature off removes its components as one unit** (#96). With VMs present, turning Virtualization off keeps KubeVirt, CDI, virtctl, Hangar and hangar-node-agent. In v2.6.6, CDI and virtctl could be removed while KubeVirt refused. Every member of the feature shows the same `uninstall refused: <member>: <reason>`. Once nothing refuses, the components go in reverse dependency order: the consoles, then CDI, then KubeVirt; for Rook: Cairn, then `ceph-csi-drivers`, then `rook-ceph`. A component that waits for its turn shows `uninstall queued: waiting for <component> to be uninstalled first`. The metadata service goes with Virtualization: while the group is held it keeps serving the VMs, and it is uninstalled last, after KubeVirt. The Hangar and Cairn consoles stay in Headlamp while their feature's components are still installed, so the steps the refusal names can be done there.
- **KubeVirt's `workloadUpdateMethods` is `[LiveMigrate]`** and belongs to the release. A list set by hand (with `Evict`, say) is put back at the next apply. After a KubeVirt upgrade, KubeVirt live-migrates the VMIs that still run an older virt-launcher.
- **`componentOverrides.headlamp` plugin lists are merged by name** with the release's (initContainers, volumes, volumeMounts). Before, they replaced them.
  - An override that adds a plugin keeps the release's plugins.
  - A copy of a plugin the release pins (same image repository, other tag) follows the release's tag.
  - An entry with another repository replaces the release's.
  - An explicitly empty list still empties it.
- **Failed components are retried sooner**: after 30 s, 1 min 30 s, 3 min 30 s and 7 min 30 s, then every 5 minutes. Before, every 5 minutes. A failed PostInstall step runs again.
- **Waiting is not failing.** A component that waits for something (Rook below 3 nodes) shows `Installed`, `waiting: <reason>`, and the ReleaseManifest stays Ready.
- **Every write of the operator is attributed to the field manager `k4all-operator`**, hooks included (before, some were `manager`). Consoles read k4all's fields by that name.
- **New installs** get `features.virt.metadata: {enabled: true, scope: Labelled}`, which does nothing while Virtualization is off, `features.rook.enabled: false` and `nodes.kubelet.maxPods: 250`. The 250 pods are what kubeadm already gave new installs since v2.6.5, now owned by k4all.

### Upgrading from v2.6.x

- **v2.7.0 is a minor**, a mandatory stop. `k4all-upgrade` runs it on command, not in the maintenance window: `sudo k4all-upgrade plan`, then `sudo k4all-upgrade run`, or a ClusterUpgrade from the addon's Upgrades page. Nodes on v2.6.0 – v2.6.6 take v2.6.7 first (`minFrom: v2.6.7`), and the plan shows both hops.
- **The hop:** new image and reboot. Then, on the bootstrap node, the sync starts k4all-operator v0.6.0 first and applies the components after it.
- **kubevirt-manager is removed at the sync, unless it is `Unmanaged`.** The operator deletes its Deployment, Service, ServiceAccount and its 4 ClusterRoles and bindings. It keeps what is still in use, and the addon's Components page lists it:
  - the PriorityClasses `vm-standard` and `vm-preemptible`, while a Pod, VM, VMI, VM replica set or VM pool names them. kubevirt-manager wrote them into every VM it created, and without them those VMs could neither start nor live-migrate;
  - the CRD `images.kubevirt-manager.io`, while it holds images;
  - the namespace `kubevirt-manager`, while your objects are in it.

  VMs, VMIs, DataVolumes and PVCs are not touched. To keep kubevirt-manager, set it to `management: Unmanaged` in the ReleaseManifest before the hop: the sync keeps an Unmanaged component as it is. A cluster restored from 1.x has it Unmanaged already, and it keeps running next to Hangar; removing it is up to you. `bootc rollback` does not bring a removed kubevirt-manager back.
- **With Virtualization on, the sync also installs** Hangar, `hangar-node-agent` and snapshot-controller. Headlamp restarts with the k4all addon 0.2.0 and Hangar's plugin.
- **KubeVirt and Cilium are applied once more.**
  - KubeVirt is applied without upstream's empty fields and with `workloadUpdateMethods: [LiveMigrate]`. Your feature gates and `permittedHostDevices` stay. Gates set before v2.7.0 are not k4all's, so none are removed. virt-api, virt-controller and virt-handler do not restart: they move only with their node's drain. Running VMs keep running.
  - Cilium is applied with the `cilium-config` it already has. Its agents do not restart.
- **Your ClusterConfig does not change.** The new fields can be set only once the cluster runs k4all-operator v0.6.0, because the v2.6.x CRD drops fields it does not know. The metadata service, Rook and node settings stay off until you set them. To leave out Hangar's node agent, set `features.virt.hangar.nodeAgent: false` after the hop: the operator then removes it, and keeps `hangar-system` while other objects are in it.
- **A maxPods you set by hand** (on clusters installed before v2.6.5) stays as it is. To let k4all own it, set the same value on the Node settings page: the rollout restarts no kubelet.
- **Node settings need every node on v2.7.0.** Nodes still on an older release are skipped (`NodesSkipped`), and they get the settings after their hop.
- **`PodNetworkOverlap` can be True on Cilium clusters installed before v2.7.0**, which run the `10.0.0.0/8` pool. k4all never changes a running pool: Cilium cannot change the CIDRs of a running pool, only add new ones. Read the condition's message before you add nodes, because a node that gets an overlapping pod CIDR keeps it. For VMs, set `networks[].pod.vmNetworkCIDR` on each VM to a network outside the pod network.
- **Never run an older operator again.** `bootc rollback` brings back the old OS, not the old cluster state (CRD, operator, removed kubevirt-manager), and v0.6.0 refuses downgrades (#77).

### Known behaviour

- **Some KubeVirt gates restart KubeVirt's infra.** Turning on or off one of `PersistentReservation`, `Template`, `ExternalNetResourceInjection`, `ConfigurableHypervisor`, `VMStatsCollector`, `Plugins` or `OptOutRoleAggregation` through the ClusterConfig restarts virt-api, virt-controller, virt-handler, virt-exportproxy and virt-template once, as it does when set by hand. VMs keep running.
- **Metadata service:**
  - On a served VM's first start under the policy, a masquerade NIC with no `macAddress` gets a MAC derived from the VM's UID (`02:` plus its first 5 bytes). It keeps that MAC from then on, so the guest's network configuration survives restarts. A MAC set in the spec (Hangar sets one) is never changed.
  - User-data comes from the VM's own cloud-init volume, which also gives the guest a disk that cloud-init prefers. The service mostly serves identity, SSH keys, vendor-data and tokens. VMs with only bridge or OVS interfaces are not served.
  - Turning the service off (`features.virt.metadata.enabled: false`) deletes its policies and the per-VM Secrets at once. A running VM keeps its server until its pod goes, and the server answers 503 meanwhile; a VM that restarts gets neither the server nor its k4all MAC.
- **Kernel arguments** (hugepages, IOMMU) live in the OS deployment. A `bootc rollback` boots the previous deployment with the kernel arguments it had. A change of kernel arguments makes a new deployment of the same release, so afterwards `bootc rollback` boots the same release with the old arguments, and the release before it is no longer reachable that way.
- **A VM that cannot live-migrate holds the drain of its node** (node settings, ClusterUpgrade) when its eviction strategy is `LiveMigrate`. VMs that kubevirt-manager created on TopoLVM are like that. The rollout's status message names the VM: stop it until the node is done.
- **A namespace with Hangar-protected objects stays `Terminating`** until their protection is turned off.
- **virt-operator restarts twice at each KubeVirt apply** (k4all-operator#44, also in v2.6.x): k4all applies upstream's Deployment, then its patch. VMs and the rest of KubeVirt's infra are not affected.
- **Not in v2.7.0:**
  - switching the CNI and turning the OVS bridge on or off: read-only in the addon, "coming with k4all-operator v0.7.0";
  - NFS StorageClasses and moving volumes between StorageClasses (VolumeMove);
  - node settings per node group;
  - user-data for VMs without a cloud-init disk.
- **Known issues**, to be fixed in v2.7.1:
  - when kubevirt-manager's image catalog is empty, its removal leaves the empty CRD `images.kubevirt-manager.io`. It is harmless; `kubectl delete crd images.kubevirt-manager.io` removes it (k4all-operator#45);
  - after `sync-manifest` finishes a sync an abandoned hop left behind, `k4all-upgrade status` may print `Rollback: … (a rollback by hand?)` although the node runs the newer release. Only that line is wrong (#112).
